## 8. Error responses

Every non-2xx response uses the same shape:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Human-readable summary",
    "details": {}
  }
}
```

| Status | Meaning | When to use |
| --- | --- | --- |
| `400` | Bad request | Malformed JSON or missing required parameter |
| `401` | Unauthorized | Missing or invalid credential |
| `403` | Forbidden | Authenticated but not allowed |
| `404` | Not found | Resource does not exist |
| `409` | Conflict | Duplicate or state conflict |
| `422` | Validation failed | Well-formed body with invalid values |
| `500` | Server error | Unexpected backend failure |

Rules:

- `code` is stable and machine-readable; `message` may change.
- Never return stack traces or internal paths.
- The frontend must handle every error status listed for the endpoints it calls.

## 11. Integration rules

1. **Contract first.** No endpoint is implemented until it appears here with status `Agreed`.
2. **No unilateral changes.** A field rename, type change, or new endpoint is proposed to the Team Lead, approved, written here, then implemented. Both sides are notified.
3. **Exact matching.** Paths, methods, field names, types, and status codes must match this document. "Close enough" is an integration bug.
4. **Mocks match the contract.** If the frontend mocks data before the backend is ready, the mock uses these exact shapes.
5. **Errors are part of the contract.** The frontend handles the documented error statuses; the backend never returns an undocumented shape.
6. **Environment values are not documented here.** Variable names belong in `docs/ARCHITECTURE.md`; values belong in local `.env` files.
7. **Database changes ship as migrations or setup scripts**, committed to the repository.
8. **CORS is configured** for the frontend origin listed in section 2, including the methods and headers in use.
